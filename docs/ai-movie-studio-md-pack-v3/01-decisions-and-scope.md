## A. 3주차(MVP)에서 반드시 하는 것

### MVP DoD (01/23 금 종료 기준)
- 로그인/회원가입
- 프로젝트 생성 → AI 시나리오 → 씬 자동 생성
- 씬 편집(Vue Flow): 마스터/그리드/샷/영상 노드 생성 및 상태 표시
- AI 이미지/영상 생성(Job) + 완료/실패 실시간 반영(WS)
- 영상 확정 → 타임라인 반영 → **최소 병합(무오디오, concat)** → 다운로드

### 기술/구조 결정(변경 금지 기준)
- **API Server**: Spring Boot (REST) + WebSocket
- **Job Queue**: **Redis Streams + Consumer Group**
- **Worker**: 이미지/영상/병합(FFmpeg) 각각 **별도 프로세스(컨테이너)**
- **스토리지**: S3 + Presigned URL

## B. WebRTC (5주차) 스코프 결정

### 이번 프로젝트(6주)에서 “협업”의 핵심 목표
- **통화 유지(라우트 이동해도 끊기지 않음)**
- 누가 어디서 작업 중인지 보이는 **Presence + Cursor/Selection**
- 빠른 의사소통을 위한 **음성 통화 + 채팅**

### 확정: v1 협업 기능(5주차 DoD)
- **음성 통화(최대 6명)**
- **텍스트 채팅(WebSocket)**
- Presence(누가 접속, 어떤 화면/씬/노드)
- Cursor/Selection(“마우스 커서+이름”, “선택한 노드 하이라이트”)
- Follow(상대가 보는 씬/노드로 따라가기: 버튼 1개)

### 제외(또는 스트레치)
- **영상(카메라) 통화: 제외** — 리소스/UX 대비 효용 낮음, 이슈(권한/네트워크/레이아웃) 증가
- 화면 공유: 기본 제외(필요 시 스트레치)

## C. Mesh vs SFU 선택(왜 Mesh로 시작하나)

- **P2P Mesh**: 참가자들이 서로 직접 연결(각자 N-1로 업로드/다운로드)
  - 장점: 서버(미디어) 없이 구현 가능, MVP 빠름
  - 단점: 인원이 늘수록 업로드가 기하급수로 증가(6명 이상부터 부담)

- **SFU(Selective Forwarding Unit)**: 클라이언트는 서버(SFU)와만 연결, 서버가 미디어를 중계
  - 장점: 참가자 증가에 강함(대규모)
  - 단점: 서버 구축/운영 난이도↑, 비용/시간↑

**결정**: 이번엔 최대 6명 기준 → **Mesh로 충분**. (문제 생기면 6주차 이후 SFU 검토)

## D. TURN 서버(왜 필요하고 어디에 두나)

### TURN 역할
- WebRTC는 원래 P2P 직결을 시도하지만, 회사망/공유기/NAT/방화벽 때문에 실패하는 경우가 흔함
- 이때 **TURN 서버(coturn)** 가 “릴레이(중계)” 역할을 해주면 연결 성공률이 올라감

### 이번 프로젝트 기준
- **STUN**: 무료 공개 STUN 서버 또는 coturn STUN 기능 사용
- **TURN**: EC2 1대에 coturn 올려서 사용 가능(단, 보안/포트 오픈/요금 주의)

> 운영 체크리스트는 `09-webrtc-collab-week5.md` 안에 포함

## E. CRDT/Yjs 동시 편집 범위 결정

### 왜 “노드 그래프 전체 CRDT”가 난이도가 높나
- Vue Flow 그래프는 단순 텍스트가 아니라 **노드/엣지/좌표/선택 상태/드래그** 등 이벤트가 많음
- CRDT로 모두 동기화하려면
  - 작은 이벤트 폭주(thrashing),
  - 버전/충돌/Undo/Redo,
  - 연결 끊김 복구(replay)
  같은 이슈를 다 잡아야 함

### 결정: v1 협업은 CRDT 없이도 “효용”을 만든다
- **Presence + Cursor/Selection + Follow + Soft Lock** 만으로도
  - “지금 누가 어디를 만지고 있는지”가 보이고
  - 충돌(동시에 한 노드 수정)을 크게 줄임
- 실제 데이터 동기화는
  - **REST/WS로 서버에 저장 → 서버가 WS로 브로드캐스트**
  - 다른 사람 화면에 “즉시 반영”은 가능

### Soft Lock(권장)
- 노드 단위 잠금 + (필요하면) 텍스트 필드 단위 잠금
- 목적: 같은 노드/필드를 동시에 편집하지 않게 “가볍게” 막기

### Yjs/CRDT 적용은 스트레치(선택)
- 만약 시간이 남으면
  - **스토리보드 텍스트/간단 문서(예: 오브젝트 시트)** 처럼
  - 구조가 단순한 대상에만 Yjs를 적용하는 건 가능

관련 상세: `10-yjs-crdt-decision.md`

## F. 자동 저장(Autosave) 결정

- 기본: **디바운스 저장(예: 500ms)** + blur 시 즉시 저장 + 10초 주기 안전 저장
- 이유: UX 좋고, 서버 부담도 과하지 않음(특히 디바운스면)
- 충돌 최소화: Soft Lock + 서버 버전(optimistic lock) 옵션

## G. 용어 한 줄 정의

- **API Server**: 유저 요청 처리(REST) + 상태 알림(WS) + Job 발행(Streams)
- **Dispatcher**: API Server 안에서 “Job 생성 → Streams publish” 하는 모듈/클래스
- **Worker**: Streams에서 Job을 가져가 실제 작업(이미지/영상/병합)을 수행하는 프로세스
- **WebSocket(WS)**: 브라우저에 “실시간 이벤트”를 푸시하는 통신
- **Presence**: 누가 접속했고 어떤 화면/씬/노드를 보고 있는지
- **Cursor/Selection**: 마우스 커서 위치/선택 노드 표시
- **Soft Lock**: “동시에 편집하지 말자”를 가볍게 강제(강제 락이 아니라 UX 기반)
