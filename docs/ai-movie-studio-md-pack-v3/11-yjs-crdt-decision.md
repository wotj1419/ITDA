# 11. Yjs/CRDT를 5주차에서 "필수"로 두지 않은 이유와 향후 계획

## 1) 결론
- 5주차 협업 MVP는 **Presence/Cursor/Selection/Soft Lock + WebRTC 음성 + 채팅**으로 충분히 임팩트를 만들 수 있음
- Vue Flow 노드 그래프 전체를 CRDT로 동기화하는 것은 **구현/QA/디버깅 난이도가 급격히 증가**하므로 6주차 버퍼 또는 차기 버전으로 미룸

---

## 2) "노드 그래프 CRDT"가 어려워지는 핵심 이유(기술적으로)

### 2.1 그래프 구조는 충돌이 다양함
- 노드 추가/삭제/이동
- 엣지 연결/해제
- 노드 데이터(prompt, options) 수정
- 드래그 중간 상태(연속 좌표 업데이트)까지 동기화하면 트래픽 증폭

### 2.2 Vue Flow(그래프 UI)의 내부 상태까지 고려해야 함
- 단순히 DB 모델을 CRDT로 합치는 것만으로 끝나지 않음
- 프론트에서는 드래그/선택/뷰포트/임시 연결선 같은 "UI 상태"가 있고, 이것을 어디까지 동기화할지 정해야 함

### 2.3 서버 저장(persistence)까지 포함하면 설계가 한 단계 더 어려워짐
- CRDT 문서(Y.Doc)를 어디에 저장할지
- 문서 버전/마이그레이션(스키마 변경) 대응
- 권한/감사 로그(누가 무엇을 바꿨는지) 등 운영 요구

---

## 3) 그럼에도 CRDT가 의미 있는 지점
- 같은 대상을 여러 명이 동시에 다듬어야 하는 경우
  - 긴 텍스트(시나리오 문서, 프롬프트 공동 편집)
  - 스토리보드 그리드의 카드 설명/메모(동시 편집이 자주 발생)
  - 노드 그래프 자체를 "두 사람이 동시에" 많이 만지는 팀 프로세스

현재 팀 프로세스가 "각자 다른 노드를 분업"에 가깝다면, 5주차에는 CRDT 없이도 협업 체감이 충분히 나올 확률이 높음.

---

## 4) CRDT 저장에서 자주 나오는 2가지 용어

### 4.1 세션 동기화(Session Sync)
- "지금 접속해 있는 사람들끼리" 실시간으로 동기화하는 것
- 보통은 웹소켓으로 Yjs 업데이트를 브로드캐스트

### 4.2 최소 저장(Minimal Persistence)
- 실시간 동기화는 하되, 저장은 자주 하지 않고(또는 특정 시점에만) 저장하는 방식
- 예:
  - 5초마다 디바운스 저장
  - 사용자가 씬을 떠날 때 저장
  - 20~50개의 업데이트가 쌓이면 저장
- 장점: 저장 비용/부하 감소
- 단점: 서버/클라이언트 장애 시 "마지막 저장 시점" 이후 변경이 유실될 수 있음

---

## 5) 6주차 버퍼 또는 차기 버전에서의 "가벼운 CRDT" 제안
- 그래프 전체 CRDT가 아니라, 효용이 큰 부분만 우선 적용
  1) 시나리오 텍스트 편집(긴 문장 공동 수정)
  2) 스토리보드 카드의 메모/설명
- 노드 그래프 CRDT는 "충분히 필요하다고 판단되면" 별도 스프린트로 분리
  - 스토리보드 그리드의 카드 설명/메모
- 단, 그래프 전체 CRDT보다 "텍스트/간단 테이블" CRDT가 ROI가 더 높을 수 있음

---

## 4) CRDT 저장: "세션 동기화" vs "최소 저장"이 의미하는 것

### A) 세션 동기화(Session Sync)
- 의미: 참가자들이 같은 문서에 붙어있는 동안, 변경 사항을 실시간으로 주고받아 모두가 같은 상태를 유지
- 구현: 보통 WebSocket 기반(Yjs provider)
- 특징: **"지금 함께 작업"**에 강함

### B) 최소 저장(Minimal Persistence)
- 의미: 실시간 동기화는 하되, 서버 저장은 "주기" 또는 "스냅샷" 단위로 최소화
- 예시
  - N초마다 스냅샷 저장
  - 문서가 idle(변경 없음) 상태일 때 저장
  - 세션 종료(마지막 사용자 나감) 시 저장
- 장점: DB/스토리지 부하 감소, 구현 단순화
- 단점: 서버 장애 시 직전 변경이 일부 유실될 수 있음(저장 주기에 따라)

> 너가 말한 "B가 당연한가?"에 대한 답: **대부분의 MVP에서는 B가 더 현실적**입니다.
> (완전 실시간 저장을 하면 쓰기 트래픽/락/버전 문제가 곧바로 운영 이슈가 됨)

---

## 5) 우리가 선택한 방향(5주차)
- CRDT는 필수에서 제외
- Presence/Cursor/Selection/Soft Lock으로 협업 체감을 만든다
- CRDT가 꼭 필요해지는지(텍스트, 스토리보드 등)는 6주차 데모 이후 판단
  - N초마다 스냅샷 저장
  - 사용자가 "저장"을 눌렀을 때 저장
  - 문서가 닫힐 때(leave) 저장
- 장점: DB/스토리지 비용과 복구 복잡도를 줄임
- 단점: 서버가 죽는 순간 일부 변경이 유실될 수 있음(저장 주기에 따라)

### 이번 프로젝트에서의 선택
- 5주차는 CRDT 자체를 필수로 하지 않음
- 6주차 버퍼 또는 차기 버전에서 CRDT를 넣게 된다면
  - 텍스트/스토리보드 같은 단순 데이터에 먼저 적용
  - 저장은 "주기 스냅샷 + 마지막 저장" 방식으로 시작하는 게 안전

---

## 5) 만약 다음 버전에서 CRDT를 도입한다면(추천 단계)
1. Awareness(커서/선택) + Presence는 CRDT 없이 유지
2. "텍스트" 하나(예: 시나리오 메모)만 Yjs로 붙여서 운영 감 잡기
3. 안정화되면 스토리보드 그리드의 카드 텍스트/메모로 확장
4. 그래프 전체 CRDT는 마지막(정말 필요할 때)
2. "텍스트" 하나(예: 시나리오 문서)만 Yjs로 도입
3. 안정화 후 스토리보드 그리드(카드 리스트)로 확장
4. 그래프 전체 동기화는 마지막(가장 위험/고난이도)
