# 09. 5주차 협업(WebRTC) 구현 가이드(결정안 포함)

## 1) 이번 팀의 결정(왜 이렇게 했나)

### 결정 A: 영상은 제외, **음성 통화 + 채팅**으로 간다
- 이유
  - 6명 영상은 브라우저/네트워크/디바이스 편차로 장애가 자주 발생
  - 데모에서 가장 중요한 것은 "협업이 된다"는 체감이며, 음성+presence+cursor로 충분히 만들 수 있음
  - 영상/화면공유는 구현뿐 아니라 QA/예외처리(권한/재연결/대역폭) 부담이 크게 증가

### 결정 B: Topology는 **P2P Mesh(최대 6명)**
- 이유
  - 6명 Mesh는 구현이 단순하고 서버 비용이 낮음
  - SFU는 서버 구축/운영 난이도와 디버깅 난이도가 큼
  - Mesh로 시작하고, 필요하면 이후 SFU로 확장 가능

### 결정 C: TURN 서버는 준비한다(필수에 가깝다)
- 이유
  - 회사/학교/공용망 환경에서는 NAT/방화벽 때문에 P2P가 직접 연결되지 않는 케이스가 존재
  - STUN만으로 해결되지 않는 경우에 TURN이 릴레이 역할을 함

---

## 2) P2P Mesh vs SFU 차이(핵심만)

### P2P Mesh
- 각 참가자가 **모든 참가자와 직접 연결**(peer connection 다중 생성)
- 장점: 구현 간단, 별도 미디어 서버 없음
- 단점: 인원이 늘수록 각 클라이언트의 업/다운 대역폭과 CPU 부담이 증가
- 이번 프로젝트: **6명 정도면 Mesh로 실험/데모 가능**

### SFU(Selective Forwarding Unit)
- 참가자는 **SFU 서버 1곳에만 업로드**하고, SFU가 다른 참가자에게 전달
- 장점: 인원이 늘어도 각 참가자의 업로드 부담이 작음
- 단점: SFU 구축/운영 난이도, 서버 비용, 장애 포인트 증가

---

## 3) STUN / TURN / ICE (실무 관점)

### STUN
- 클라이언트가 "내 공인 IP/포트"를 알아내기 위한 서버
- 대부분의 일반 환경에서는 STUN만으로도 P2P 연결이 됨

### TURN
- STUN으로도 연결이 안 되는 환경에서 **서버가 미디어를 릴레이(중계)**
- TURN은 트래픽을 직접 받기 때문에 비용/부하가 커질 수 있음
- 이번 프로젝트: Jenkins EC2에 coturn을 올려서 테스트할 수 있음(5주차)

### ICE
- 브라우저가 STUN/TURN 후보(candidate)를 모아서 최적의 경로를 찾는 과정

---

## 4) 우리가 구현하는 WebRTC 구조(서버는 무엇을 하나)

### (1) 시그널링 서버(필수)
- WebRTC 자체는 "서로 연결"만 담당하고, 연결을 시작하려면 SDP/ICE 교환이 필요
- 이 교환을 중계하는 서버가 필요하고, 우리는 **WebSocket으로 구현**

### (2) 채팅 서버(같은 WebSocket에서 함께 처리 가능)
- 텍스트 메시지는 WebRTC 데이터 채널로도 가능하지만, MVP는 단순하게 WebSocket broadcast로 처리

---

## 5) 통화 유지(라우트 이동) 구현 규칙

### 목표
- 사용자가 `프로젝트 상세 ↔ 씬 편집` 화면을 이동해도 통화가 끊기지 않는다.

### 방법(권장)
- FE에서 WebRTC/WS를 **전역 싱글톤(스토어)로 유지**
  - 예: Pinia store, 또는 별도 `CallManager` 모듈을 단일 인스턴스로 유지
- 화면은 바뀌어도 "플로팅 바 UI"만 재렌더링 되도록
- 페이지 새로고침은 끊기는 것으로 처리하되, "재입장" UX 제공

---

## 6) 예외 처리 체크리스트(최소)
- 마이크 권한 거부 → 권한 요청 재시도 UI
- 마이크 장치 변경 → 트랙 교체
- 참가자 입장/퇴장 이벤트 표시
- 네트워크 끊김 → 재연결(시그널링 WS 재연결 + peer 재협상)

---

## 7) 5주차 작업 분해(누가 뭘 만들면 되나)

### BE(김은서)
- WS 시그널링 서버
  - room join/leave
  - offer/answer/candidate relay
- 채팅 broadcast

### BE(장현준)
- TURN 서버(coturn) 설정 + 테스트 시나리오 정리
- ICE 서버 리스트 배포 전략(DEV/PROD)

### FE(박재서)
- 플로팅 협업 바 UI(통화 버튼/상태/마이크 on-off)
- 오디오 장치 선택, mute

### FE(이진원)
- 채팅 UI 패널
- presence 표시 UI(참여자 목록/현재 위치)

### BE/FE(이용호 + 이진원)
- presence 이벤트 스키마 정의/송수신(WS)
