## 0) 이 문서의 목적

- **처음 보는 팀원도**
  1) 전체 아키텍처가 어떻게 생겼는지,
  2) 지금 당장 내가 무엇을 구현해야 하는지,
  3) 다른 사람이 만든 결과물과 어떻게 연결되는지
  를 바로 이해하도록 만든 실행용 일정표입니다.

- 일정표는 “태스크 나열”보다 **병렬 개발이 가능한 경계(contracts)를 먼저 고정**하는 방식으로 구성했습니다.

## 1) W3~W6 큰 그림 (병렬화 포인트)

### ✅ 병렬화의 핵심 원칙

1. **API 서버(스프링)**는 “요청을 받아서 Job을 만들고 상태를 관리”하는 곳
2. **Worker(별도 프로세스)**는 “Job을 가져가서 외부 AI / FFmpeg 작업을 실제로 수행”하는 곳
3. **WebSocket(서버→FE push)**은 “Job 상태 변화(완료/실패)를 즉시 화면에 반영”하는 용도

즉, 팀이 병렬로 일하려면 아래 3가지 **공통 계약(Contract)**을 W3 초반에 고정해야 합니다.

- (A) **Job 스키마**: Job이 어떤 필드를 갖고 어떤 상태로 변하는지
- (B) **Queue 규칙**: Redis Streams 토픽명/consumer group/ACK/재처리 규칙
- (C) **WS 이벤트 스키마**: job.done/job.failed 메시지 payload 규격

> 위 3개만 고정되면, FE는 Worker가 없어도 “상태 표시 UI”를 만들 수 있고,
> Worker는 FE가 없어도 “Job 처리 + 상태 업데이트”를 만들 수 있고,
> API 서버는 외부 AI가 없어도 “Job 생성/조회/재시도”를 만들 수 있습니다.

---

## 2) 용어 한 줄 정의 (팀 공유용)

- **API Server (Spring)**: 로그인/프로젝트/씬/노드/타임라인 API 제공 + Job 생성/상태 저장 + WS 발행
- **Dispatcher**: “API 서버 내부에서 Job을 Queue에 넣는(발행하는) 컴포넌트”
- **Queue (Redis Streams)**: Job을 Worker에게 전달하는 메시지 스트림
- **Worker**: Streams에서 Job을 읽고 실제 처리를 수행한 뒤 결과를 저장하고 상태를 갱신
- **WebSocket**: FE가 구독하고 있다가 Job 결과를 즉시 받는 “서버→클라 푸시 채널”

> Dispatcher는 **서버를 분리하라는 뜻이 아니라** “코드 레벨의 역할 분리(인터페이스)”입니다.

## 4) W3 MVP Definition of Done (01/19~01/23)

### ✅ W3 종료 시 “데모 1회 완주” 기준
1) 로그인/회원가입
2) 프로젝트 생성
3) AI 시나리오 생성 → 씬 자동 생성
4) 씬 편집(Vue Flow): 마스터/그리드/샷/영상 노드 생성 및 상태 표시
5) 이미지/영상 생성(Job) → **완료/실패 실시간 반영(WS)**
6) 영상 확정 → 타임라인 반영 → **최소 병합(무오디오 concat)** → 다운로드

> MVP 병합은 “동작 우선”: 720p / H.264 / 오디오 없음 / 트랜지션 없음
