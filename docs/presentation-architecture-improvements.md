# 발표용 아키텍처 & 기술 개선 정리 (Easy Version)

발표 자료에 “우리 서비스가 어떻게 돌아가는지”와 “기술적으로 무엇을 개선했는지”를 **한 번에 이해**할 수 있도록 정리한 문서입니다.

## 1. 한 줄 요약
AI 호출/영상 병합 같은 무거운 작업을 **Job(작업)으로 비동기화**하고, 결과는 **실시간(WebSocket)** 으로 알리며, 파일은 **S3(presigned URL)** 로 안전하게 제공하는 “협업형 AI 영화 제작 스튜디오”입니다.

## 2. 전체 구조 (큰 그림)

### 2.1 구성요소
- 사용자 브라우저 (Vue)
- Edge / Reverse Proxy (Nginx)
- API 서버 (Spring Boot)
- DB (MySQL)
- Redis
- 비동기 Worker (이미지 생성, 영상 생성, FFmpeg 병합)
- Storage (S3, presigned URL)
- Observability (Prometheus/Grafana)

### 2.2 텍스트 다이어그램

```text
[Browser: Vue]
  |  HTTP (CRUD / Job 요청)
  v
[Nginx]
  |  /api -> Spring API
  |  /ws  -> WebSocket(STOMP)
  v
[Spring API]
  |  1) 요청 검증/권한 확인
  |  2) Job 생성 (DB)
  |  3) Redis Streams에 enqueue
  |  4) 상태 조회 API 제공 + WebSocket 이벤트 발행
  |
  +--> [MySQL] (프로젝트/씬/노드/Job/Asset)
  +--> [Redis] (Streams + Pub/Sub)
  |
  v
[Workers]
  |  - Image Worker (Gemini)
  |  - Video Worker (Veo)
  |  - Merge Worker (FFmpeg)
  v
[S3]
  |  presigned URL로 결과 전달
  v
[Browser: Vue]
  |  WebSocket(job.done/job.failed)로 즉시 UI 갱신
```

## 3. “Job 비동기화”가 핵심인 이유

### 3.1 우리가 풀고 싶은 문제
AI 호출/영상 병합은 시간이 오래 걸릴 수 있습니다.
- 사용자가 기다리는 동안 요청이 타임아웃 나기 쉬움
- 서버가 동기 처리하면 스레드가 묶여서 동시 처리량이 급감
- 장애/재시작 시 “진행 중 작업”이 유실되기 쉬움

### 3.2 해결 전략
요청을 “즉시 처리”하지 않고 “작업(Job)으로 등록”해서 백그라운드에서 처리합니다.
- API는 빠르게 `jobId`만 반환
- Worker가 실제 AI/FFmpeg 작업 수행
- Job 상태가 바뀌면 프론트는 상태를 갱신

### 3.3 상태 전이(가시성) 설계
Job은 상태가 명확해야 UI/운영이 쉬워집니다.
- `PENDING`: 큐에 들어가 대기
- `RUNNING`: 워커가 가져가 실행 중
- `SUCCEEDED`: 성공
- `FAILED`: 실패

추가로 실무에서 중요한 포인트가 있습니다.
- “중복 실행 방지”를 위해, 실행 시작 시점에 상태를 원자적으로 `RUNNING`으로 바꾸는 방식(CAS)을 사용
- “중복 클릭/재시도”를 안전하게 처리하기 위해 `idempotencyKey`로 같은 작업이면 같은 Job을 재사용

## 4. 실시간(WebSocket) 설계 포인트

### 4.1 왜 WebSocket인가
Job 완료까지 기다렸다가 새로고침하거나 계속 폴링하면 UX가 나빠집니다.
- WebSocket 이벤트로 “작업 완료/실패”를 즉시 푸시
- 프론트는 노드 배지/썸네일/토스트를 바로 갱신

### 4.2 보안과 권한(발표에서 신뢰도 포인트)
WebSocket도 결국 “데이터 통로”라 인증/인가가 중요합니다.
- CONNECT 시점에 JWT를 검증
- SUBSCRIBE/SEND 시점에 “프로젝트 접근 권한”을 확인
- 한 세션에서 이미 검증한 프로젝트는 캐시하여 성능을 확보

### 4.3 확장성(멀티 서버 대비)
서버가 여러 대일 때도 같은 채널로 이벤트를 전달할 수 있어야 합니다.
- Redis Pub/Sub로 브로드캐스트
- Redis가 불가능한 경우 WebSocket으로 직접 전송하는 fallback 로직

## 5. 파일 전달(S3 presigned) 설계 포인트

### 5.1 왜 presigned URL인가
이미지/영상 같은 대용량 파일을 API 서버가 직접 서빙하면 부담이 큽니다.
- S3가 파일 전송을 담당
- API는 “권한이 있는 사용자에게 일시적으로 접근 가능한 URL”을 발급

### 5.2 체감 성능 개선 요소
다운로드/미리보기 체감은 결국 “캐싱”과 “URL 재사용”이 큽니다.
- presigned URL을 캐시해서 같은 파일을 반복 요청해도 비용/지연을 줄임
- 콘텐츠 타입에 따라 Cache-Control 정책을 분리해 브라우저 캐시 효율을 올림

## 6. 기술적으로 개선한 내용(발표에 넣기 좋은 사례)

## 6.1 비용/쿼터 이슈(429 Resource Exhausted) 개선
문제 상황
- 프롬프트 미리보기(preview)를 입력 변화마다 자동 호출하면 AI 요청이 폭증
- 결과적으로 429가 반복되고, 비용/쿼터가 빠르게 소진

개선
- 미리보기는 “사용자 명시 행동(버튼)” 기반으로만 실행
- 프롬프트 생성 성공 시에만 강제 preview를 호출하는 식으로 호출량을 통제

발표 메시지 예시
- “AI 호출을 UX 이벤트에 묶지 않고, 의도된 액션에서만 실행해 쿼터 리스크를 줄였다”

## 6.2 협업 중 편집 지연(락 경합) 분석과 개선 방향
문제 상황
- 이미지 생성 중에 노드 추가/삭제가 “바로 반영되지 않고 나중에 몰아서 처리”되는 UX 발생

원인(핵심만)
- 생성 경로와 편집 경로가 같은 DB row에 `FOR UPDATE`로 락을 걸어 경합
- 긴 처리 구간이 트랜잭션/락 범위에 포함되면, 다른 요청이 대기열에 쌓임

개선 방향
- 생성(generate) 경로에서 “꼭 필요한 구간만” 락을 잡도록 분리
- 번역/프롬프트 렌더 같은 시간이 걸리는 구간은 락 밖으로 빼서 편집 응답성을 확보

발표 메시지 예시
- “협업 UX의 병목을 UI가 아니라 DB 동시성 관점에서 진단했고, 락 범위 축소로 근본 해결을 설계했다”

## 6.3 프론트 품질 개선(유지보수성과 일관성)
문제 상황
- 씬 에디터는 기능이 빠르게 늘어나면서 중복/비슷한 로직이 분산되기 쉬움
- 큰 파일(거대 store)이 생기면 버그 추적과 테스트가 어려움

개선
- 노드 생성 플로우(프롬프트 생성, 승인, Job 실행, 폴링, 결과 반영)를 `useNodeGeneration` 같은 공통 로직으로 통합
- SceneNode store를 모듈로 분해해서 책임을 분리
- API DTO 타입과 UI 타입을 분리하여 “서버 변경”이 “UI 모델”에 무분별하게 번지는 것을 차단

발표 메시지 예시
- “복잡한 생성 플로우를 컴포저블로 표준화해 중복과 버그 확률을 줄였다”

## 6.4 CI/CD & 운영 자동화(신뢰도 상승 포인트)
무엇을 자동화했나
- 백엔드/프론트 빌드
- 도커 이미지 빌드
- 특정 브랜치 조건에서 배포 수행
- 빌드/배포 결과를 협업툴로 알림

발표 메시지 예시
- “개발 속도뿐 아니라 배포 재현성과 피드백 속도를 자동화로 확보했다”

## 7. 발표 슬라이드 추천 구성(짧게)
1. 문제 정의: “AI/영상 생성은 무겁고, 협업은 즉시성이 필요하다”
2. 아키텍처 한 장: Job 비동기 + WebSocket + S3 presigned
3. 핵심 흐름: Generate 요청부터 결과 반영까지 시퀀스(5~7단계)
4. 기술 개선 1: 429 문제 해결(호출량 통제)
5. 기술 개선 2: 락 경합 분석(협업 UX 병목 진단)
6. 기술 개선 3: 프론트 구조화(중복 제거/모듈화)
7. DevOps: CI/CD 파이프라인으로 운영 신뢰도 확보

## 8. 용어 미니 사전(발표에서 질문 대비)
- Job: 시간이 오래 걸리는 작업을 “등록하고 추적”하기 위한 단위
- Redis Streams: 작업을 줄 세워 넣는 큐(메시지 스트림)
- Worker: 큐에서 Job을 가져가 실제 AI/FFmpeg를 실행하는 실행기
- presigned URL: 제한 시간 동안만 유효한 S3 다운로드 URL
- STOMP: WebSocket 위에서 쓰는 메시징 프로토콜(구독/발행 모델)
