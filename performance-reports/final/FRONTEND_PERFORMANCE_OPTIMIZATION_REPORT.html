Frontend Performance Optimization Report

잇다 랜딩 페이지 초기 로딩 비용 최적화

프론트엔드 담당자로서 Vercel 정적 배포 환경의 Lighthouse 결과를 기준으로 랜딩 페이지 병목을 분석하고, UI 변화를 최소화하면서 미디어 로딩, 애니메이션 초기화, 폰트 CSS, 초기 번들, 정적 이미지를 단계적으로 개선했습니다.

성과 요약 문제 정의 전후 비교 단계별 개선 기술 근거 포트폴리오 문장 해석 주의점
91.8% Mobile 총 전송량 감소
8.18MB -> 0 Hero video 초기 전송 제거
65KB 초기 JS 전송량 감소
86.4% icon.png 파일 크기 감소

1. 성과 요약

Mobile 총 전송량 8.48MiB -> 0.70MiB 약 91.8% 감소
Desktop 총 전송량 8.51MiB -> 0.76MiB 약 91.1% 감소
Hero video 초기 전송 7.8MiB -> 0 초기 요청 제거
Lighthouse Performance Mobile 69 -> 73 Desktop은 98 -> 95

이 개선의 핵심은 Lighthouse 점수만 올리는 것이 아니라, 초기 로딩에 불필요한 대용량 리소스를 제거하고 병목의 위치를 수치로 추적한 것입니다. 최종적으로 랜딩 페이지 초기 전송량을 8MiB대에서 1MiB 미만으로 낮췄습니다.

2. 개선 전 문제 정의

최초 측정은 Vercel 정적 배포 환경에서 Chrome DevTools Lighthouse Navigation 모드로 진행했습니다. 측정 대상은 랜딩 페이지이며, 백엔드 API가 필요한 회원가입, 로그인, 프로젝트 상세, 에디터 플로우는 범위에서 제외했습니다.

Toss 외부 font CSS font 약 443~464KiB 렌더 차단 및 외부 도메인 의존 CSS 로딩 위치를 HTML preload 기반으로 변경

4. 단계별 개선 과정

Phase 1

Hero video preload 전략 변경

`preload="auto"`를 `metadata`로 바꿔 브라우저의 적극적인 선다운로드를 줄이고자 했습니다.

  • UI 변화가 가장 적은 첫 번째 실험
  • autoplay 영상에서는 여전히 일부 다운로드가 발생할 수 있음을 확인
Phase 2

Hero video poster 추가

영상 src 지연을 적용하기 전에 mockup 영역이 비어 보이지 않도록 poster 이미지를 추가했습니다.

  • 영상 로딩 전 시각 안정성 확보
  • 추후 `preload="none"`과 lazy loading을 적용할 기반 마련
Phase 3

Hero video lazy loading

IntersectionObserver로 mockup 영역 근처에 도달할 때만 video src를 연결하도록 변경했습니다.

  • scene-1.mp4 초기 전송량 약 7.8MiB -> 0
  • Mobile 총 전송량 8.48MiB -> 0.79MiB
  • 가장 큰 네트워크 병목 제거
Phase 3.5

랜딩 애니메이션 초기화 지연

Phase 3 이후 Mobile TBT가 증가해, 네트워크 병목이 JS 실행 비용으로 이동했음을 확인하고 below-the-fold 애니메이션 초기화를 지연했습니다.

  • Mobile TBT 350ms -> 0ms
  • Main-thread work 4.7s -> 3.8s
  • LandingPage long task 257ms -> 180ms
Phase 4

Toss font CSS 로딩 최적화

CSS `@import`로 불러오던 Toss font CSS를 HTML의 preconnect/preload 기반 로딩으로 조정했습니다.

  • 렌더 차단 CSS 구조 개선
  • CSS transfer 123.93KiB -> 45.71KiB 수준으로 감소
  • UI 글꼴 변경 없이 로딩 전략만 조정
Phase 4.5

Hero poster lazy loading 실험

`scene-1-poster.webp`도 초기 요청에서 제외할 수 있는지 실험했습니다. 결과적으로 현재 UI 배치에서는 observer가 page load 직후 발동했습니다.

  • poster 전송량 약 112KB 유지
  • UI 안정성을 해치지 않는 범위에서는 추가 지연 효과 제한
  • 실험 결과를 바탕으로 unused JS 분석으로 우선순위 전환
Phase 6

초기 entry JS code splitting

랜딩 페이지에서 사용하지 않는 협업/WebSocket/WebRTC 관련 코드가 `App.vue`를 통해 초기 entry에 포함되는 문제를 분리했습니다.

  • CollabRouteLayer를 `defineAsyncComponent`로 동적 로드
  • 초기 entry resourceSize 318,604 bytes -> 122,444 bytes
  • Mobile unused JavaScript 65,031 bytes -> 0
Phase 5

icon.png 이미지 용량 최적화

실제 표시 크기보다 큰 공통 아이콘 이미지를 128px 폭으로 리사이즈해 정적 이미지 payload를 줄였습니다.

  • icon.png 34,190 bytes -> 4,637 bytes
  • 파일 크기 약 86.4% 감소
  • Mobile 총 전송량 약 29.5KB 추가 감소

5. 핵심 기술 근거

5.1 IntersectionObserver로 video src 연결 지연

단순히 `preload`만 바꾸는 것으로는 autoplay video의 초기 다운로드를 완전히 제어하기 어려웠습니다. 그래서 video 태그의 `src` 자체를 조건부로 연결해, mockup 영역이 화면 근처에 들어오기 전까지 `scene-1.mp4` 요청이 발생하지 않도록 했습니다. 

<video
  :src="shouldLoadHeroVideo ? selectedHeroVideo : undefined"
  :poster="shouldLoadHeroPoster ? '/scene-1-poster.webp' : undefined"
  preload="none"
/>

5.2 Below-the-fold 애니메이션 초기화 지연

hero 영역에 필요한 애니메이션은 즉시 실행하고, features, workflow, node-edge, cta 등 화면 아래 섹션의 GSAP/ScrollTrigger 초기화는 IntersectionObserver 진입 후 실행하도록 분리했습니다. 

setupLandingAnimations()
  hero animation 즉시 초기화
  observeOnce('.features-section') 후 features animation 초기화
  observeOnce('.workflow-section') 후 workflow animation 초기화
  observeOnce('.node-edge-section') 후 node animation 초기화
  observeOnce('.cta-section') 후 cta animation 초기화

5.3 라우트 조건 기반 협업 코드 분리

최상위 `App.vue`에서 협업 UI와 collab store를 정적으로 import하면 랜딩 페이지에서도 협업 코드가 초기 번들에 포함됩니다. 이를 `CollabRouteLayer`로 분리하고, `/projects` 경로에서만 동적 로드하도록 변경했습니다. 

const CollabRouteLayer = defineAsyncComponent(() =>
  import('./components/collab/CollabRouteLayer.vue')
)

5.4 정적 이미지 크기 조정

`icon.png`는 실제 표시 크기가 대부분 24~64px인데 원본은 439x388이어서 payload가 불필요하게 컸습니다. 2x 해상도 대응을 고려해 128px 폭으로 줄이고 기존 `/icon.png` 경로는 유지했습니다.

6. 포트폴리오에 사용할 문장

요약형

Vercel 정적 배포 환경에서 Lighthouse와 Network 분석을 통해 잇다 랜딩 페이지의 초기 로딩 병목을 개선했습니다. 초기 측정 결과 전체 전송량 약 8.5MiB 중 7.8MiB가 hero video에서 발생하는 것을 확인하고, video src 지연 연결, 애니메이션 초기화 지연, font CSS 로딩 개선, 초기 entry JS code splitting, 정적 이미지 리사이즈를 단계적으로 적용했습니다. 그 결과 Mobile 총 전송량을 8.48MiB에서 0.70MiB로 약 91.8% 줄이고, 초기 video 전송량을 0으로 제거했습니다.

상세형

프론트엔드 담당자로서 랜딩 페이지 성능을 개선하기 위해 Lighthouse 측정 결과를 기반으로 병목을 단계적으로 추적했습니다. 처음에는 `preload` 전략만 조정했지만 autoplay video 특성상 초기 다운로드가 유지되는 것을 확인했고, 이후 IntersectionObserver로 video `src` 연결 시점을 지연해 `scene-1.mp4` 초기 전송량을 약 7.8MiB에서 0으로 줄였습니다. 이후 네트워크 병목이 줄어들자 Mobile TBT와 long task가 새 병목으로 드러나, hero 외 섹션의 GSAP 애니메이션 초기화를 지연했습니다. 또한 랜딩에서 사용하지 않는 협업/WebSocket 관련 코드를 route 조건 기반 동적 import로 분리해 초기 entry JS resourceSize를 318,604 bytes에서 122,444 bytes로 줄였고, 공통 아이콘 이미지를 34,190 bytes에서 4,637 bytes로 최적화했습니다.

면접 답변형

이 작업에서 가장 중요하게 본 것은 점수 하나가 아니라 병목의 이동을 추적하는 과정이었습니다. 처음에는 총 전송량 대부분이 hero video에서 발생했기 때문에 네트워크 병목을 먼저 제거했습니다. 이후 video 요청이 사라지자 TBT와 long task가 새로 드러났고, 애니메이션 초기화 시점을 조정했습니다. 또 Lighthouse의 unused JavaScript 항목을 따라가 보니 랜딩에서 쓰지 않는 협업 코드가 최상위 컴포넌트에 정적 import되어 있었고, 이를 라우트 단위 chunk로 분리했습니다. 최종적으로 초기 총 전송량을 8MiB대에서 1MiB 미만으로 줄였습니다.

7. 결과 해석과 주의점

  • Lighthouse 점수는 보조 지표입니다. Desktop은 개선 전 98점으로 이미 높았기 때문에 점수 상승보다 전송량 감소가 더 중요한 성과입니다.
  • SEO 점수는 비교 지표에서 제외합니다. 최종 측정은 Vercel Preview URL에서 진행되어 인덱싱 제한 영향으로 SEO 점수가 낮게 측정될 수 있습니다.
  • Mobile TBT는 측정 편차가 있습니다. Phase 6과 Phase 5의 LandingPage long task는 비슷했지만 TBT 집계 결과가 크게 달라졌습니다.
  • 남은 개선 후보는 font와 runtime layout입니다. Toss font self-hosting, font-weight 축소, LandingPage Style/Layout 비용 분석은 추가 개선 후보입니다.

최종 포트폴리오에는 “Performance 점수를 크게 올렸다”보다 “Lighthouse와 Network 분석을 통해 초기 전송량을 약 91% 줄이고, hero video 초기 요청과 unused JS를 제거했다”라고 쓰는 것이 가장 정확합니다.
